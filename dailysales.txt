# Chai Flow – Daily Sales, Payments, Credit, and Expense Report

I want to create a new page in my existing **Chai Flow Tea Shop Management System** to display complete daily sales, customer bill details, payment collections, credit sales, and expenses.

First, inspect my existing frontend, FastAPI backend, database models, order records, payment records, customer credit records, and expense management system. Implement this feature using the existing project architecture and database. Do not create a separate application or duplicate existing data.

## 1. Create a New Daily Report Page

Create a new page named **Daily Sales & Expenses Report** in the admin panel sidebar.

Requirements:

* Allow the administrator to select a specific date.
* By default, display the current day's report.
* Provide Previous Day and Next Day navigation.
* Add a Refresh button to reload the report.
* Display the report for the selected date only.
* Use the existing Chai Flow light theme and responsive design.

## 2. Daily Financial Summary

At the top of the page, display summary cards showing:

* **Total Sales:** Total value of all eligible bills created on the selected date.
* **Cash Received:** Total cash payments actually collected.
* **UPI Received:** Total UPI payments actually collected.
* **Card Received:** Total card payments actually collected.
* **Credit Sales:** Total amount added to customers' outstanding credit through eligible sales.
* **Credit Payments Collected:** Total payments received against previously outstanding customer credit.
* **Total Expenses:** Total expenses recorded for the selected date.
* **Total Payments Received:** Total actual payments collected through cash, UPI, card, and other supported payment methods.
* **Net Cash Flow:** Total payments received minus total expenses paid.
* **Outstanding Credit:** Current outstanding customer credit balance, with an option to view the selected day's credit changes separately.

Clearly distinguish sales from payments received. Credit sales must not be counted as cash received until the customer actually pays.

## 3. Display Every Bill Line by Line

Create a detailed table showing every bill or order for the selected date.

Display these columns:

1. Bill Number / Order ID
2. Bill Date and Time
3. Customer Name
4. Customer Mobile Number
5. Product Name
6. Quantity
7. Unit Price
8. Line Total
9. Bill Total
10. Amount Paid
11. Payment Method
12. Credit Amount
13. Order Status

If a bill contains multiple products, show each product on a separate line while clearly grouping the lines under the same bill number.

For each bill, display:

* Customer details.
* All products purchased.
* Quantity of each product.
* Price per product.
* Total bill amount.
* Amount paid immediately.
* Payment method and payment status.
* Amount added to customer credit.
* Any applicable discount or adjustment supported by the existing system.

Provide a View Details action to open the complete bill or order.

Do not duplicate the bill total or payment amount when calculating totals from multiple product lines.

## 4. Daily Payment Collection Details

Create a separate section named **Payment Collection Details**.

Display each payment transaction with:

* Transaction ID.
* Payment date and time.
* Bill Number or related order.
* Customer Name.
* Customer Mobile Number.
* Payment Method: Cash, UPI, Card, or another supported method.
* Payment Amount.
* Payment Type: New Sale Payment or Previous Credit Payment.
* Transaction Reference, when available.
* Payment Status.

Allow the administrator to filter transactions by payment method and payment type.

Only count successfully recorded payments as collected money. Do not count pending, failed, or cancelled payments as received.

If customers make partial payments or pay their outstanding credit later, show those transactions separately and calculate the totals correctly.

## 5. Daily Customer Credit Details

Create a section named **Credit Sales and Collections**.

Display the following for every relevant customer:

* Customer ID.
* Customer Name.
* Mobile Number.
* Bill Number, when applicable.
* Previous Outstanding Credit.
* New Credit Added.
* Credit Payment Received.
* Credit Adjustment, if any.
* Current Outstanding Credit.
* Transaction Date and Time.

Provide a way to open the customer's complete credit transaction history.

Calculate outstanding credit using the existing credit-management rules. Do not treat the customer's credit limit as the outstanding balance.

Distinguish between:

* Credit created from sales on the selected date.
* Payments collected against old credit.
* Manual credit increases or decreases.
* The customer's current outstanding credit balance.

## 6. Daily Expenses Details

Create a separate section named **Daily Expenses**.

Display each expense recorded on the selected date, with these columns:

1. Expense ID.
2. Expense Date and Time.
3. Expense Category.
4. Expense Description.
5. Amount.
6. Payment Method.
7. Paid By / Recorded By, when available.
8. Notes.
9. Expense Status.

Include categories such as tea powder, milk, sugar, snacks, supplies, rent, electricity, transport, salaries, and miscellaneous expenses where appropriate.

Use the existing expense categories if the application already has them.

At the bottom, display the total eligible expenses for the selected date.

If the application supports expense creation and editing, reuse those existing features rather than duplicating them.

## 7. Daily Profit and Financial Reconciliation

Create a financial summary that explains how the daily amounts relate to one another.

Display:

* Total eligible sales.
* Total sales paid immediately.
* Total credit sales.
* Total actual payments received.
* Total payments received against previous credit.
* Total expenses.
* Net cash flow.
* Net sales less expenses, clearly labelled as a preliminary operating surplus/deficit rather than verified accounting profit.

Use consistent business rules so that:

* A credit sale is included in sales but not in cash collected.
* A later credit payment increases collections but does not create new sales.
* An expense is included only according to its recorded date and valid status.
* Cancelled or voided bills are excluded from sales totals according to the existing order rules.
* Refunds and reversals are accounted for correctly if supported by the application.
* No transaction is counted twice.

Show the calculation definitions in a small information section so the administrator can understand how each total is calculated.

## 8. Search, Filters, and Navigation

Provide:

* Date selection.
* Search by customer name or mobile number.
* Search by bill number.
* Filter by payment method.
* Filter by payment status.
* Filter by order status.
* Filter by credit or non-credit sales.
* Pagination for large reports.

Changing filters must update the displayed records and totals consistently.

## 9. Export and Print

Add these actions:

* Export daily report to PDF.
* Export bill and transaction details to CSV or Excel, depending on existing project capabilities.
* Print the daily report.
* Include the selected date, summary totals, bill details, payment collections, credit transactions, expenses, and final reconciliation in the exported report.

Use existing report-generation libraries and utilities where possible.

## 10. Backend and Database Requirements

Inspect the existing FastAPI APIs and database models before making changes.

* Reuse existing orders, bills, customers, payments, credit transactions, and expense tables.
* Create new API endpoints only where necessary.
* Use SQLAlchemy queries and database aggregation where appropriate.
* Use the existing database and authentication configuration.
* Validate the selected date and filter parameters.
* Apply administrator authorization to the report endpoints.
* Use the correct timezone consistently for daily filtering.
* Filter using the appropriate business date and timestamps.
* Prevent duplicate records and double counting when joining bills with multiple product lines or payments.
* Return a clear, consistent API response with summary totals and detailed records.
* Handle missing customer details, empty reports, invalid dates, and API errors gracefully.
* Do not change existing financial records or invent missing transaction data.

## 11. Testing and Final Verification

Test the following scenarios:

1. The report displays the correct data for the selected date.
2. All bills show the correct customer and product details.
3. Bills with multiple products do not cause duplicate sales totals.
4. Partial payments are calculated correctly.
5. Credit sales are separated from money actually collected.
6. Payments against previous credit are counted as collections, not new sales.
7. Expenses are included on the correct date.
8. Cancelled bills, failed payments, refunds, and reversals are handled according to existing business rules.
9. Summary cards match the detailed transactions.
10. Date filters, searches, pagination, PDF export, CSV/Excel export, and printing work correctly.
11. The report is responsive and accessible only to authorized administrators.
12. Existing Chai Flow features continue to work.
